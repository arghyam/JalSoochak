# Water Service Situation Reports — Calculation Reference

The authoritative specification for the three WhatsApp PDF reports JalSoochak sends to field officers:

| Report                                             | Recipient                | Schedule (IST) | Data window                                                    |
| -------------------------------------------------- | ------------------------ | -------------- | -------------------------------------------------------------- |
| **A. Daily Water Service Situation Report**        | `SECTION_OFFICER` only   | 16:00 daily    | **today** 00:00 → 16:00                                        |
| **B. Weekly Water Service Situation Report (SO)**  | `SECTION_OFFICER`        | Monday 09:00¹  | **previous** full week, `weekStartDay` → +6d (default Mon–Sun) |
| **C. Weekly Water Service Situation Report (SDO)** | `SUB_DIVISIONAL_OFFICER` | Monday 09:00¹  | **previous** full week, `weekStartDay` → +6d (default Mon–Sun) |

¹ Both the firing time and the window start day are per-tenant configurable; the values shown are the defaults.

Source templates: `backend/SO daily report.docx`, `backend/SO weekly report.docx`,
`backend/SDO weekly report.docx`.

Every field below names the table and column it is read from, the formula, and the rounding. Section
[9](#9-verification-queries) gives a runnable SQL block per KPI so a generated PDF can be checked
against the database.

> **This document supersedes** `DAILY_REPORT_DATA_SOURCES.md` and `DAILY_REPORT_VERIFICATION_QUERIES.md`,
> which describe the previous D-1 report sent to both SO and SDO.

## 1. Which database holds what

Two databases are involved, and the split is a privacy boundary, not just a convenience.

|            | Operational                                                           | Warehouse                                                    |
| ---------- | --------------------------------------------------------------------- | ------------------------------------------------------------ |
| Schemas    | `common_schema` + one `tenant_<state_code>` per state                 | `analytics_schema`                                           |
| Holds      | system of record, **all PII** (names, phones — AES-encrypted at rest) | denormalised facts and dimensions, **no PII**                |
| Migrations | `backend/database/`                                                   | `backend/analytics-service/src/main/resources/db/migration/` |
| Used for   | scheme names, IMIS ids, Jal Mitra / officer contacts, village names   | every KPI number and every scheme-id list                    |

**analytics-service never reads PII and never touches `common_schema`.** It computes KPIs and emits
scheme ids and user ids; message-service resolves those into names and phone numbers from the
operational schema at render time, immediately before drawing the PDF.

### Pipeline

```
tenant-service                        analytics-service                   message-service
 TenantSchedulerManager                AnalyticsKafkaConsumer              KafkaConsumer
  └ one CronTrigger per tenant (IST)    ├ DAILY_REPORT_REQUEST              └ NotificationEventRouter
 DailySituationReportSchedulerService   │  └ DailySituationReportService       ├ resolve PII (tenant schema)
 WeeklySituationReportSchedulerService  └ WEEKLY_REPORT_REQUEST               ├ DailyReportPdfService
  └ publish <X>_REPORT_REQUEST             └ WeeklySituationReportService     │ WeeklyReportPdfService  (PDFBox)
    (officer ids only — no PII)          └ publish <X>_REPORT_KPIS            ├ MinioStorageService
                                                                              └ GlificWhatsAppService
```

Transport is Kafka topic `common-topic` throughout. A `correlationId` generated by the scheduler
threads one run's log lines across all three services.

## 2. Shared definitions

Every number in all three reports is built from these. They are deliberately single definitions —
where the same idea was previously expressed two different ways, the reports disagreed with the
dashboard.

### 2.1 The officer's scheme set

```sql
SELECT DISTINCT usm.scheme_id
FROM analytics_schema.dim_user_scheme_mapping_table usm
JOIN analytics_schema.dim_scheme_table s
  ON s.scheme_id = usm.scheme_id AND s.tenant_id = usm.tenant_id
WHERE usm.user_id = :officer_user_id
  AND usm.tenant_id = :tenant_id
  {{WS}}
```

`dim_user_scheme_mapping_table` carries both operators and officers; the officer's role is
established upstream in tenant-service when recipients are enumerated, not here.

### 2.2 `{{WS}}` — the handed-over filter

Rendered by `analytics-service/.../helper/DashboardWorkStatusFilter.java`, aliased to the
`dim_scheme_table` alias `s`. Three tiers, **first non-empty wins**:

1. the tenant's own `dim_tenant_table.included_work_statuses`
2. the national row, `dim_tenant_table` where `tenant_id = 0`
3. the env default `analytics.dashboard.included-work-statuses`, default `ARRAY[4]`

`work_status = 4` is `HANDED_OVER` (`SchemeWorkStatus`: 1 Ongoing, 2 Completed, 3 Not Started,
4 Handed Over). If the effective set resolves to `NULL` the filter is disabled and all schemes pass;
otherwise a scheme passes only when `work_status = ANY(set)` — **a `NULL` `work_status` never matches
and is excluded.**

```sql
-- {{WS}} expansion, appended after an existing WHERE/ON on dim_scheme_table alias `s`
AND (
  COALESCE(
    NULLIF((SELECT dt_own.included_work_statuses FROM analytics_schema.dim_tenant_table dt_own
             WHERE dt_own.tenant_id = s.tenant_id), '{}'::int[]),
    NULLIF((SELECT dt_nat.included_work_statuses FROM analytics_schema.dim_tenant_table dt_nat
             WHERE dt_nat.tenant_id = 0), '{}'::int[]),
    :env_work_statuses
  ) IS NULL
  OR s.work_status = ANY(COALESCE(
    NULLIF((SELECT dt_own.included_work_statuses FROM analytics_schema.dim_tenant_table dt_own
             WHERE dt_own.tenant_id = s.tenant_id), '{}'::int[]),
    NULLIF((SELECT dt_nat.included_work_statuses FROM analytics_schema.dim_tenant_table dt_nat
             WHERE dt_nat.tenant_id = 0), '{}'::int[]),
    :env_work_statuses
  ))
)
```

> `{{WS}}` is applied to **every** query in all three
> reports.

### 2.3 Scheme fan-out — always de-duplicate before summing

`dim_scheme_table` holds **one row per scheme per LGD/department mapping**, so a scheme that spans
three villages appears three times. Any `SUM` of a per-scheme attribute (`fhtc_count`,
`house_hold_count`, `planned_fhtc`) must collapse the scheme to one row first:

```sql
SELECT DISTINCT ON (s.tenant_id, s.scheme_id)
       s.tenant_id, s.scheme_id, s.fhtc_count, s.house_hold_count
FROM analytics_schema.dim_scheme_table s
WHERE s.tenant_id = :tenant_id {{WS}}
ORDER BY s.tenant_id, s.scheme_id,
         s.fhtc_count DESC NULLS LAST,
         s.house_hold_count DESC NULLS LAST,
         s.planned_fhtc DESC NULLS LAST
```

`COUNT(DISTINCT scheme_id)` is naturally safe; `SUM` is not.

**There are two different de-duplication orderings in this codebase and they are not interchangeable:**

| Ordering                                                                                                            | Picks                           | Use for                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fhtc_count DESC NULLS LAST, house_hold_count DESC NULLS LAST, planned_fhtc DESC NULLS LAST`                        | the row with the largest counts | **summing scheme attributes** — FHTC totals, population, LPCD denominators (the block above)                                                            |
| `updated_at DESC NULLS LAST, created_at DESC NULLS LAST, id DESC` — the `{{CSR}}` / `canonicalSchemeRowOrder` token | the most recently written row   | reading **scheme status or name** (`work_status`, `operating_status`, `scheme_name`), because `DimensionServiceImpl` rewrites only the one row it finds |

All the reports' FHTC and population maths uses the first. `{{CSR}}` is the right choice only where a
scheme's current _status_ matters, which none of these three reports reads directly.

### 2.4 `{{LWQ}}` — the de-duplicated water source

`fact_water_quantity_table` is written by find-latest-and-update, so a concurrent replay could leave
two rows for one scheme-day. Every water aggregation reads through this instead of the raw table:

```sql
(SELECT DISTINCT ON (fwq.tenant_id, fwq.scheme_id, fwq.date) fwq.*
   FROM analytics_schema.fact_water_quantity_table fwq
  ORDER BY fwq.tenant_id, fwq.scheme_id, fwq.date, fwq.updated_at DESC, fwq.id DESC)
```

`water_quantity` is in **litres** (`BIGINT`, since analytics migration V45; it was cubic metres
before). Telemetry converts at the boundary via `WaterVolumeUnits.cubicMetresToLitres`.

### 2.5 `{{SWD}}` — "did this scheme supply water on this day"

```sql
((f.submission_status = 1 OR f.submission_status IS NULL) AND f.water_quantity > 0)
```

`submission_status` 1 = SUBMITTED, 0 = NOT_SUBMITTED; `NULL` is a legacy direct-event row. A
NOT_SUBMITTED/outage day never counts as supply even if it carries a positive volume.

> the KPI labelled "Schemes
> Supplying Water" actually measured "schemes that submitted a reading", and "Regular Supply %"
> measured submission regularity. All three reports use `{{SWD}}`, the same definition the
> dashboards use.

### 2.6 `{{SWS}}` — supplied volume in litres

Deliberately the same qualifying condition as `{{SWD}}`, so volume and supply-days cannot drift:

```sql
COALESCE(SUM(CASE WHEN (f.submission_status = 1 OR f.submission_status IS NULL)
                   AND f.water_quantity > 0
                  THEN f.water_quantity ELSE 0 END), 0)::bigint
```

### 2.7 Population

```
population(scheme set) = Σ fhtc_count (de-duplicated, §2.3)
                       × COALESCE(dim_tenant_table.person_count_per_household, 5)
```

`fhtc_count` is **achieved functional household tap connections** — the households actually connected.
`house_hold_count` (households in the scheme's area, connected or not) exists on the same table but is
**not** used by any report figure; the two differ and mixing them would put the HH percentages and the
LPCD on different bases.

`person_count_per_household` is per tenant, seeded from tenant config; `5` is the fallback.

### 2.8 Rounding

Every ratio, percentage and LPCD value: `BigDecimal.valueOf(x).setScale(1, RoundingMode.HALF_UP)` —
**one decimal place**. Counts are integers. A ratio whose denominator is zero is reported as `0`, never
as an error or a blank.

### 2.9 Time zones

This is the most common source of off-by-one-day bugs in this codebase.

| Column                                              | Zone                              |
| --------------------------------------------------- | --------------------------------- |
| `fact_water_quantity_table.date`                    | **IST calendar day**              |
| `fact_meter_reading_table.reading_date`             | **IST calendar day**              |
| `fact_meter_reading_table.reading_at`               | **IST wall-clock**                |
| `anomaly_table.created_at`                          | **UTC, naive** (no offset stored) |
| `created_at` / `updated_at` audit columns generally | UTC                               |

So an IST calendar day `D` maps to the half-open UTC interval
`[D 00:00 − 5:30, D+1 00:00 − 5:30)`. In code this is
`DailySituationReportService.istDayStartUtc(day)`:

```java
day.atStartOfDay(ZoneId.of("Asia/Kolkata")).withZoneSameInstant(ZoneOffset.UTC).toLocalDateTime()
```

All scheduling runs in `Asia/Kolkata` (`CronTrigger` with an explicit `TimeZone`).

## 3. Report A — Daily (Section Officer)

Sent at the tenant's configured daily time (default 16:00 IST) covering **the same day so far**.

### 3.1 The window

Water and reading facts are written in real time: telemetry publishes `WATER_QUANTITY_RECORDED` and
`METER_READING_RECORDED` asynchronously the moment a reading is accepted, stamped with the IST
calendar day. A 16:00 run therefore sees exactly what was submitted between 00:00 and 16:00 — the
window is enforced by _when the job runs_, not by a filter.

To make a re-run reproducible, the scheduler puts its run instant on the request event as `cutoffIst`,
and queries bound by it **wherever a timestamp column exists**:

| Source                      | Bounded by                                                               |
| --------------------------- | ------------------------------------------------------------------------ |
| `anomaly_table`             | `created_at ∈ [istDayStartUtc(today), istToUtc(cutoffIst))`              |
| `fact_meter_reading_table`  | `reading_at < cutoffIst`                                                 |
| `fact_water_quantity_table` | **cannot be bounded** — the table has only `date`, no intraday timestamp |

The last row is a real limitation, recorded here rather than left to be discovered: re-running the
daily job at 18:00 for the same day will include supply recorded between 16:00 and 18:00. The
originally delivered PDF is the record of what was true at the cut-off.

### 3.2 Header

| Line                                      | Source                                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `Section-Officer: <name>`                 | `tenant_<code>.user_table.title` by officer id, AES-decrypted                                            |
| `Date: <dd MMMM yyyy>`                    | today (IST)                                                                                              |
| `Reporting Period: 00:00 hrs – HH:MM hrs` | `HH:MM` is the tenant's **configured** daily cron time, so the line stays truthful if the schedule moves |
| Dashboard link                            | `daily-report.dashboard-url`                                                                             |

### 3.3 Section 1 — Summary

Let **T** = Total Schemes, **S** = Schemes Supplying Water, **NN** = total FHTC, **nn** = FHTC of
supplying schemes.

| Row                                                  | Source                                               | Formula                                                                                                                                                     |
| ---------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Total Schemes (Handed Over Schemes only)             | `dim_user_scheme_mapping_table` ⋈ `dim_scheme_table` | `COUNT(DISTINCT scheme_id)` with `{{WS}}`. Reuses `SchemeRegularityRepository.getSchemeCountByUser(tenantId, userId, null)`. → **T**                        |
| Schemes Supplying Water                              | `{{LWQ}}`                                            | `COUNT(DISTINCT f.scheme_id)` where `f.date = today AND {{SWD}}`, restricted to the officer's schemes → **S**                                               |
| Schemes Not having supplied Water (Till cut-off)     | _derived_                                            | `max(T − S, 0)`                                                                                                                                             |
| Number of HHs with water supply TODAY — `nn (m%)`    | `dim_scheme_table.fhtc_count`                        | `nn` = `Σ fhtc_count` (§2.3) of the **S** supplying schemes; `m` = `round1(100 × nn / NN)`                                                                  |
| Number of HHs yet to get water supply — `qq (r%)`    | _derived_                                            | `qq = NN − nn`; `r = round1(100 × qq / NN)` — computed from `qq` directly, **not** as `100 − m`, so the two percentages never sum to 100.1 through rounding |
| Average LPCD _(of schemes that have supplied water)_ | `{{LWQ}}` + `dim_scheme_table` + `dim_tenant_table`  | `round1(litres / popSupplying)`                                                                                                                             |
| Number of Anomalous Submissions                      | `analytics_schema.anomaly_table`                     | `COUNT(DISTINCT a.id)` in the window                                                                                                                        |

**NN** = `Σ fhtc_count` (§2.3) over all **T** handed-over schemes mapped to the officer.

**Average LPCD — note the denominator.** The template footnotes this KPI "_of schemes that have
supplied water_", so:

```
litres       = {{SWS}} for today over the officer's schemes
popSupplying = Σ fhtc_count of the SUPPLYING schemes only × person_count_per_household
avgLpcd      = round1(litres / popSupplying)        -- 0 when popSupplying = 0
```

Non-supplying schemes contribute nothing to `{{SWS}}`, so the numerator is identical whether taken
over **S** or **T**; only the denominator narrows. **This is the one place in the system where the LPCD
denominator is not the full scheme set** — it answers "how well did the schemes that ran actually
serve?", not "how well was the whole command area served". The weekly reports use the full set.

**Anomalous Submissions** — `deleted_at IS NULL`, joined to the officer's schemes on `scheme_id`,
`created_at` inside the UTC-converted window of §3.1. Counted `DISTINCT a.id`.

### 3.4 Section 2 — Schemes with No Water Supply (till the cut-off)

Every handed-over scheme mapped to the officer that has **no** row satisfying `{{SWD}}` for today.
This includes schemes that submitted nothing at all and schemes that submitted a NOT_SUBMITTED/outage
row.

| Column         | Source                                               | Notes                                                                                                                         |
| -------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Scheme_imis_id | `tenant_<code>.scheme_master_table.centre_scheme_id` | There is **no** `scheme_imis_id` column anywhere. `centre_scheme_id` is the IMIS id; `state_scheme_id` is the state's own id. |
| Scheme Name    | `scheme_master_table.scheme_name`                    |                                                                                                                               |
| Jal Mitra Name | `user_table.title`, AES-decrypted                    | via `user_scheme_mapping_table` ⋈ `user_table` ⋈ `common_schema.user_type_master_table` on `UPPER(c_name) = 'PUMP_OPERATOR'`  |
| Mobile No.     | `user_table.phone_number`, AES-decrypted             | several operators on one scheme are joined with `", "`                                                                        |

analytics-service emits only `scheme_id`s; message-service batch-resolves the four columns
(`resolveSchemeLabels`, `resolvePumpOperators` in `NotificationEventRouter`). Rows are ordered by
scheme name. A scheme with no mapped operator renders with blank Jal Mitra cells rather than being
dropped — the missing operator is itself the actionable information.

> **Expect this list to be long.** At 16:00 a large share of an officer's schemes may legitimately not
> have supplied yet. The PDF table paginates and repeats its header row, so the report simply grows.

### 3.5 Section 3 — Schemes with Anomalous Submissions

One row per **(scheme, anomaly type)** raised in the window.

| Column                        | Source                                                           |
| ----------------------------- | ---------------------------------------------------------------- |
| Scheme_imis_id / Scheme Name  | `scheme_master_table.centre_scheme_id` / `scheme_name`           |
| Type of Anomaly in Submission | `analytics_schema.anomaly_table.type`, mapped to a display label |
| Jal Mitra Name / Mobile No.   | as §3.4                                                          |

`anomaly_table.type` is `VARCHAR(128)` holding the enum **name**; rows written before analytics
migration V29 hold the numeric **code** as a string. The label mapping handles both
(`ANOMALY_LABELS` keyed by name, `CODE_TO_NAME` for the legacy form).

| Template label             | Enum name                    | Legacy code |
| -------------------------- | ---------------------------- | ----------- |
| Reading Less Than Previous | `READING_LESS_THAN_PREVIOUS` | 5           |
| Duplicate Image            | `DUPLICATE_IMAGE_SUBMISSION` | 4           |
| Unreadable Image           | `UNREADABLE_IMAGE`           | 1           |
| No Water Supply            | `NO_WATER_SUPPLY`            | 6           |
| Location Mismatch          | `LOCATION_MISMATCH`          | 11          |

Other types that can appear: `MANUAL_OVERRIDE` (2), `CONSECUTIVE_OVERRIDE_5_DAYS` (3),
`LOW_WATER_SUPPLY` (7), `OVER_WATER_SUPPLY` (8), `NO_SUBMISSION` (9),
`IMPLAUSIBLE_WATER_SUPPLY` (10). The section is data-driven: it renders whatever types actually
occurred, so new types appear without a code change.

**On "Location Mismatch"** — this compares the reading's `flow_reading_table.latitude`/`longitude`
against `scheme_master_table.latitude`/`longitude` and appears when the distance exceeds the
`LOCATION_AFFINITY_THRESHOLD` metres configured at system level (`tenant_id = 0`). It is raised only
for tenants whose `LOCATION_CHECK_REQUIRED` is `YES`, and only when both the reading and the scheme
have coordinates — anything missing is skipped rather than reported, so a row here always means a
real measured overshoot. Unlike every other type in this section it does **not** mean the reading
was rejected: the value is stored and counted normally. See
[location-affinity-check.md](location-affinity-check.md).

## 4. Report B — Weekly (Section Officer)

### 4.1 The window

**W** = the last COMPLETE week beginning on the tenant's configured `weekStartDay` (default Monday),
i.e. `date BETWEEN :week_start AND :week_end`, a seven-day inclusive span. A Monday 09:00 run of a
Monday-start tenant reports the week that ended the previous evening. W never includes a day that has
not finished, whatever day the job fires on.

**W-1** = the seven days immediately before W, used for the comparison column.

### 4.2 Per-scheme supply days — the building block for every section

```sql
SELECT f.scheme_id, COUNT(DISTINCT f.date) AS supply_days
FROM {{LWQ}} f
JOIN user_schemes us ON us.scheme_id = f.scheme_id
WHERE f.tenant_id = :tenant_id
  AND f.date BETWEEN :week_start AND :week_end
  AND {{SWD}}
GROUP BY f.scheme_id
```

A scheme in the officer's set with no row here has `supply_days = 0`.

### 4.3 Section 1 — Summary

Three columns: **Previous Week** (W), **Previous Week − 1** (W-1), **Trend**.

| KPI                                                     | Formula                                                  |
| ------------------------------------------------------- | -------------------------------------------------------- |
| Total Schemes                                           | `COUNT(DISTINCT scheme_id)` with `{{WS}}`                |
| Schemes Supplying Water (for minimum 1 day in the week) | schemes with `supply_days >= 1`                          |
| Schemes Not Supplying Water at all                      | schemes with `supply_days = 0`, i.e. `Total − supplying` |
| Average LPCD                                            | `round1(litresW / (population × 7))`                     |

```
litresW    = {{SWS}} over W for the officer's schemes
population = Σ fhtc_count over ALL the officer's handed-over schemes × person_count_per_household
```

**Unlike the daily report, the weekly LPCD denominator is the full scheme set** — the weekly template
carries no "supplying only" footnote, and over a whole week the question being asked is how well the
command area as a whole was served. The `× 7` makes it a per-day figure comparable with the daily
report's LPCD.

**Trend** = `value(W) − value(W-1)`, rendered `▲ +n` / `▼ -n` / `—`. Colour follows _direction of
improvement_, not sign: green when the officer is better off. `Schemes Not Supplying Water at all` is
in the inverted set, so a fall there is green.

**Total Schemes is not historical.** `dim_user_scheme_mapping_table` holds current mappings only, with
no validity dates, so both week columns report today's mapping count. If schemes were reassigned, the
W-1 figure will not match what last week's report actually said.

### 4.4 Sections 2–4 — scheme lists

All three share the columns `S. No. | Scheme Name | Jal Mitra | Jal Mitra Phone Number`, resolved from
the operational schema exactly as §3.4.

| Section                                       | Filter                                                    |
| --------------------------------------------- | --------------------------------------------------------- |
| 2. Schemes with no supply (the whole week)    | `supply_days = 0`                                         |
| 3. Schemes with 1 to 3 days of supply         | `supply_days BETWEEN 1 AND 3`                             |
| 4. Schemes with ≤15 LPCD supply over the week | per-scheme weekly LPCD `<= 15` **and** `supply_days >= 1` |

**Per-scheme weekly LPCD:**

```
schemeLpcdW = round1( {{SWS}} for that scheme over W
                      / (schemeFhtc × person_count_per_household × 7) )
```

where `schemeFhtc` is that scheme's de-duplicated `fhtc_count` (§2.3).

Two deliberate exclusions from section 4:

- **`fhtc_count = 0` schemes are excluded.** Their LPCD is undefined, not zero — including them would
  fill the list with schemes that have no connections to serve.
- **`supply_days = 0` schemes are excluded.** They are already listed in full in section 2; repeating
  them here would make section 4 read as "no supply" rather than "under-supply", which is the
  actionable distinction. Section 4 answers: _of the schemes that did run, which ran too weakly?_

The 15 LPCD bar is configurable (§7) — it is a service-level judgement, not a constant of the domain.

## 5. Report C — Weekly (Sub-Divisional Officer)

Same window and comparison week as Report B, scoped to the SDO's own mapped handed-over schemes.

### 5.1 Section 1 — Summary

Three columns: **Last Week** (W), **Previous Week** (W-1), **Trend**.

| KPI                                              | Formula                                               |
| ------------------------------------------------ | ----------------------------------------------------- |
| Total Handed-Over Schemes                        | `COUNT(DISTINCT scheme_id)` with `{{WS}}`             |
| Schemes Supplying Water (≥4 days in the week)    | schemes with `supply_days >= 4`                       |
| Schemes Not Supplying Water (0 days in the week) | schemes with `supply_days = 0`                        |
| Schemes With Supply ≤15 LPCD (average)           | schemes whose weekly LPCD (§4.4) `<= 15`              |
| Average LPCD                                     | `round1(litresW / (population × 7))`, full scheme set |

> **The SO and SDO reports use different supply bars — ≥1 day and ≥4 days — and this is intentional.**
> The SO's report asks "did each of my schemes run at all this week?"; the SDO's asks "did it run
> often enough?". A consequence worth knowing before someone files it as a bug: an SO's own
> "Schemes Supplying Water" figure will normally be **higher** than the same SO's row in their SDO's
> table, even over identical schemes. Both thresholds are configurable (§7).

`Schemes Not Supplying` is the inverted KPI for trend colouring; `Schemes With Supply ≤15 LPCD` is
inverted too — fewer is better.

### 5.2 Section 2 — Section Officers Performance

One row per Section Officer under the SDO.

**There is no hierarchy column on `user_table`.** The SDO→SO relationship is _derived_ as the distinct
`SECTION_OFFICER`s sharing at least one active scheme with the SDO, resolved in tenant-service
(`NudgeRepository.findSubordinateSectionOfficerIds`) and carried on the request event as ids:

```sql
SELECT DISTINCT so_u.id
FROM tenant_xx.user_scheme_mapping_table sdo_usm
JOIN tenant_xx.user_scheme_mapping_table so_usm ON so_usm.scheme_id = sdo_usm.scheme_id
JOIN tenant_xx.user_table so_u ON so_u.id = so_usm.user_id
JOIN common_schema.user_type_master_table so_ut ON so_ut.id = so_u.user_type
WHERE sdo_usm.user_id = :sdo_user_id
  AND sdo_usm.status = 1 AND so_usm.status = 1 AND so_u.status = 1
  AND UPPER(so_ut.c_name) = 'SECTION_OFFICER'
```

Each row's KPIs are the Section 1 metrics computed **for that SO, narrowed to the schemes that SO
shares with the SDO**. The narrowing is an optional bind applied in SQL; a `NULL` disables it, so the
SDO's own totals and every standalone SO report are unaffected:

```sql
AND (CAST(:supervisor_user_id AS bigint) IS NULL
     OR EXISTS (SELECT 1
                  FROM analytics_schema.dim_user_scheme_mapping_table sup
                 WHERE sup.user_id = CAST(:supervisor_user_id AS bigint)
                   AND sup.tenant_id = usm.tenant_id
                   AND sup.scheme_id = usm.scheme_id))
```

| Column                                     | Source                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------------- |
| Section Officer Name / SO Mobile No.       | `tenant_<code>.user_table.title` / `phone_number` by SO id, AES-decrypted       |
| Total Schemes                              | that SO's schemes ∩ the SDO's schemes, `{{WS}}` applied                         |
| Schemes Supplying Water (≥4 days)          | as §5.1, over the intersection                                                  |
| Schemes Not Supplying Water (0 days)       | as §5.1, over the intersection                                                  |
| Schemes with Supply ≤15 LPCD (average)     | as §4.4, over the intersection                                                  |
| Average LPCD (total schemes under command) | `round1(litresW / (population × 7))` over the intersection, **full** scheme set |

Two consequences of the intersection, both correct and both worth stating so they are not mistaken
for defects:

- **An SO's own weekly report legitimately shows more schemes** than that officer's row here. The own
  report covers all their schemes; this row covers only the shared ones.
- **`Σ(SO Total Schemes)` equals the SDO's Total Schemes only where the SDO's schemes map 1:1 onto
  SOs.** A scheme mapped to the SDO and two SOs is counted in both rows; a scheme mapped to the SDO
  with no SO appears in no row. Both are data-quality conditions in `user_scheme_mapping_table`, not
  report logic — the report neither de-duplicates nor adds an "unassigned" row.

### 5.3 Sections 3–4 — scheme lists

Columns: `S. No | SO Name | SO Phone Number | Scheme Name | Village Name | Jal Mitra Name | Jal Mitra Phone`.

| Section                                       | Filter                                               |
| --------------------------------------------- | ---------------------------------------------------- |
| 3. Schemes with No Supply (zero days)         | `supply_days = 0`                                    |
| 4. Schemes with ≤15 LPCD supply over the week | weekly LPCD `<= 15` and `supply_days >= 1` (as §4.4) |

Two resolutions beyond those of §3.4:

**Scheme → Section Officer.** `user_scheme_mapping_table` ⋈ `user_table` ⋈
`common_schema.user_type_master_table` on `UPPER(c_name) = 'SECTION_OFFICER'`, active mapping and
active user. A scheme mapped to two SOs lists both, joined with `", "`; a scheme with no SO renders
blank.

**Scheme → Village Name.** `tenant_<code>.scheme_lgd_mapping_table` ⋈ `lgd_location_master_table`,
taking `title`. **There is no `village_table`** — villages are rows of `lgd_location_master_table` at
the deepest level of the per-tenant LGD tree (state → district → block → GP → village; levels are
configured per tenant in `location_config_master_table`). A scheme can map to several villages — this
is exactly why `dim_scheme_table` fans out (§2.3) — and **all of them are listed, joined with `", "`**.

## 6. Storage and delivery

### 6.1 MinIO object keys

| Report        | Bucket                 | Object key                                                                                  |
| ------------- | ---------------------- | ------------------------------------------------------------------------------------------- |
| A. Daily      | `daily-water-reports`  | `SO/<report-date>/daily_water_report_SECTION_OFFICER_<userId>_<report-date>.pdf`            |
| B. Weekly SO  | `weekly-water-reports` | `SO/<from>_to_<to>/weekly_water_report_SECTION_OFFICER_<userId>_<from>_to_<to>.pdf`         |
| C. Weekly SDO | `weekly-water-reports` | `SDO/<from>_to_<to>/weekly_water_report_SUB_DIVISIONAL_OFFICER_<userId>_<from>_to_<to>.pdf` |

Dates are `yyyy-MM-dd`; `<from>`/`<to>` are the first and last day of the reported week. Examples:

```
daily-water-reports/SO/2026-07-19/daily_water_report_SECTION_OFFICER_21343_2026-07-19.pdf
weekly-water-reports/SO/2026-07-13_to_2026-07-19/weekly_water_report_SECTION_OFFICER_21343_2026-07-13_to_2026-07-19.pdf
weekly-water-reports/SDO/2026-07-13_to_2026-07-19/weekly_water_report_SUB_DIVISIONAL_OFFICER_5521_2026-07-13_to_2026-07-19.pdf
```

`officerUserId` — not the officer's name — is the filename discriminator: names collide, and these
buckets are shared across every officer in every tenant, so a collision would expose one officer's
report to another.

**Both buckets must be created out of band and granted anonymous read**
(`mc anonymous set download <alias>/<bucket>`). Nothing in the application sets a bucket policy. The
officer's phone is what opens the link, so verify from outside the network before enabling delivery:

```bash
curl -sSI https://<public-host>/minio/daily-water-reports/SO/2026-07-19/<file>.pdf
```

### 6.2 WhatsApp delivery

Delivery uses Glific HSM templates in **LINK** mode: one `sendHsmMessage` whose "View Report" button
carries the object key. Parameters are `[officerName, date, urlSuffix]` — **the URL suffix must come
last**. `urlSuffix` is the MinIO URL minus `minio.base-url + "/"`, i.e. `<bucket>/<object key>`.

The button's URL **prefix** is frozen at Meta approval and must equal `minio.base-url` + `/`. Because
the bucket and folders travel inside the variable, **changing the bucket or adding folders needs no
new template approval** — but each environment still needs its own approved template, since the hosts
differ.

`minio.endpoint` (where this service uploads, internal) and `minio.base-url` (the public prefix handed
to Glific) are different addresses. Confusing them produces a link the officer cannot open.

## 7. Configuration

### 7.1 Schedules — per tenant

Both crons are stored in `common_schema.tenant_config_master_table` and read at schedule time, with
`application.yml` as the fallback. `TenantSchedulerManager` holds one `ScheduledFuture` per job per
tenant and re-schedules on config change without a restart.

| Config key                     | JSON                                                                                 | Default                                 |
| ------------------------------ | ------------------------------------------------------------------------------------ | --------------------------------------- |
| `DAILY_SITUATION_REPORT_TIME`  | `{"dailyReport":{"schedule":{"hour":16,"minute":0}}}`                                | 16:00 IST daily                         |
| `WEEKLY_SITUATION_REPORT_TIME` | `{"weeklyReport":{"schedule":{"dayOfWeek":1,"hour":9,"minute":0},"weekStartDay":1}}` | Fires Monday 09:00 IST, reports Mon–Sun |

`dayOfWeek` and `weekStartDay` both follow the cron convention 0–7 where both 0 and 7 are Sunday; 1 is
Monday. `schedule` is when the job fires, `weekStartDay` is which seven days it covers — they are
independent, and the scheduler WARNs when they differ. Written
through `PUT /api/v1/tenants/{tenantId}/config`, which requires `SUPER_USER`, or `STATE_ADMIN` on
one's own tenant.

## 8. Known gaps and deliberate choices

1. **"HHs with water supply" is scheme-attributed, not measured.** Supply is recorded per scheme, never
   per household. The figure is the FHTC of schemes that supplied — it assumes every connected
   household on a supplying scheme received water, which a scheme-level meter cannot confirm. (§3.3)
2. **`Total Schemes` is not historical.** Scheme mappings carry no validity dates, so week-over-week
   comparisons use today's mapping for both columns. (§4.3)
3. **Schemes with `fhtc_count = 0` are excluded from LPCD lists**, since their LPCD is undefined rather
   than zero. They still appear in scheme counts and in the no-supply lists. (§4.4)

## 9. Verification queries

One runnable block per KPI, reproducing the repository logic exactly. Substitute:

- `:tenant_id`, `:officer_user_id`
- `:report_date` — the day report A covers (today, IST)
- `:week_start` / `:week_end` — first and last day of W; `:prev_week_start` / `:prev_week_end` for W-1
- `:sdo_user_id` — only for the Report C breakdown
- `:env_work_statuses` — `ARRAY[4]::int[]` unless `ANALYTICS_DASHBOARD_INCLUDED_WORK_STATUSES` is set
- `:pph` — `dim_tenant_table.person_count_per_household`, default 5
- `tenant_xx` — the tenant schema, e.g. `tenant_mp`

Each block repeats the scheme-scoping CTE so it is self-contained. `{{WS}}` is written out in full in
the first block and referred to as `/* {{WS}} — see §2.2 */` thereafter to keep the rest readable.

### 9.1 Total Schemes (A, B, C)

```sql
SELECT COUNT(DISTINCT usm.scheme_id)::int AS total_schemes
FROM analytics_schema.dim_user_scheme_mapping_table usm
JOIN analytics_schema.dim_scheme_table s
  ON s.scheme_id = usm.scheme_id AND s.tenant_id = usm.tenant_id
WHERE usm.user_id = :officer_user_id
  AND usm.tenant_id = :tenant_id
  AND (
    COALESCE(
      NULLIF((SELECT dt_own.included_work_statuses FROM analytics_schema.dim_tenant_table dt_own
               WHERE dt_own.tenant_id = s.tenant_id), '{}'::int[]),
      NULLIF((SELECT dt_nat.included_work_statuses FROM analytics_schema.dim_tenant_table dt_nat
               WHERE dt_nat.tenant_id = 0), '{}'::int[]),
      :env_work_statuses
    ) IS NULL
    OR s.work_status = ANY(COALESCE(
      NULLIF((SELECT dt_own.included_work_statuses FROM analytics_schema.dim_tenant_table dt_own
               WHERE dt_own.tenant_id = s.tenant_id), '{}'::int[]),
      NULLIF((SELECT dt_nat.included_work_statuses FROM analytics_schema.dim_tenant_table dt_nat
               WHERE dt_nat.tenant_id = 0), '{}'::int[]),
      :env_work_statuses
    ))
  );
```

### 9.2 Schemes Supplying Water today (A)

```sql
WITH user_schemes AS (
    SELECT DISTINCT usm.scheme_id
    FROM analytics_schema.dim_user_scheme_mapping_table usm
    JOIN analytics_schema.dim_scheme_table s
      ON s.scheme_id = usm.scheme_id AND s.tenant_id = usm.tenant_id
    WHERE usm.user_id = :officer_user_id AND usm.tenant_id = :tenant_id
      /* {{WS}} — see §2.2 */
),
latest_wq AS (
    SELECT DISTINCT ON (fwq.tenant_id, fwq.scheme_id, fwq.date) fwq.*
    FROM analytics_schema.fact_water_quantity_table fwq
    ORDER BY fwq.tenant_id, fwq.scheme_id, fwq.date, fwq.updated_at DESC, fwq.id DESC
)
SELECT COUNT(DISTINCT f.scheme_id)::int AS schemes_supplying
FROM latest_wq f
JOIN user_schemes us ON us.scheme_id = f.scheme_id
WHERE f.tenant_id = :tenant_id
  AND f.date = :report_date

```

`Schemes Not having supplied Water` = §9.1 − this, floored at 0. No separate query.

### 9.3 Households with / without supply today (A)

```sql
WITH user_schemes AS ( /* as §9.2 */ ),
latest_wq AS ( /* as §9.2 */ ),
scheme_fhtc AS (
    SELECT DISTINCT ON (s.tenant_id, s.scheme_id) s.scheme_id, COALESCE(s.fhtc_count, 0) AS fhtc
    FROM analytics_schema.dim_scheme_table s
    JOIN user_schemes us ON us.scheme_id = s.scheme_id
    WHERE s.tenant_id = :tenant_id
      /* {{WS}} — see §2.2 */
    ORDER BY s.tenant_id, s.scheme_id,
             s.fhtc_count DESC NULLS LAST, s.house_hold_count DESC NULLS LAST, s.planned_fhtc DESC NULLS LAST
),
supplying AS (
    SELECT DISTINCT f.scheme_id
    FROM latest_wq f
    JOIN user_schemes us ON us.scheme_id = f.scheme_id
    WHERE f.tenant_id = :tenant_id AND f.date = :report_date
      AND ((f.submission_status = 1 OR f.submission_status IS NULL) AND f.water_quantity > 0)
)
SELECT
    COALESCE(SUM(sf.fhtc) FILTER (WHERE sp.scheme_id IS NOT NULL), 0)::bigint AS hh_with_supply,   -- nn
    COALESCE(SUM(sf.fhtc), 0)::bigint                                         AS hh_total,          -- NN
    COALESCE(SUM(sf.fhtc) FILTER (WHERE sp.scheme_id IS NULL), 0)::bigint     AS hh_without_supply, -- qq
    ROUND(100.0 * COALESCE(SUM(sf.fhtc) FILTER (WHERE sp.scheme_id IS NOT NULL), 0)
          / NULLIF(SUM(sf.fhtc), 0), 1)                                        AS pct_with_supply,   -- m%
    ROUND(100.0 * COALESCE(SUM(sf.fhtc) FILTER (WHERE sp.scheme_id IS NULL), 0)
          / NULLIF(SUM(sf.fhtc), 0), 1)                                        AS pct_without_supply -- r%
FROM scheme_fhtc sf
LEFT JOIN supplying sp ON sp.scheme_id = sf.scheme_id;
```

### 9.4 Average LPCD of supplying schemes (A)

```sql
WITH user_schemes AS ( /* as §9.2 */ ),
latest_wq AS ( /* as §9.2 */ ),
scheme_fhtc AS ( /* as §9.3 */ ),
supplying AS ( /* as §9.3 */ ),
litres AS (
    SELECT COALESCE(SUM(CASE WHEN (f.submission_status = 1 OR f.submission_status IS NULL)
                              AND f.water_quantity > 0
                             THEN f.water_quantity ELSE 0 END), 0)::bigint AS litres_supplied
    FROM latest_wq f
    JOIN user_schemes us ON us.scheme_id = f.scheme_id
    WHERE f.tenant_id = :tenant_id AND f.date = :report_date
),
pop AS (
    SELECT COALESCE(SUM(sf.fhtc), 0)::bigint * :pph AS population_supplying
    FROM scheme_fhtc sf
    JOIN supplying sp ON sp.scheme_id = sf.scheme_id
)
SELECT litres.litres_supplied,
       pop.population_supplying,
       CASE WHEN pop.population_supplying > 0
            THEN ROUND(litres.litres_supplied::numeric / pop.population_supplying, 1)
            ELSE 0 END AS avg_lpcd
FROM litres, pop;
```

### 9.7 Per-scheme supply days and weekly LPCD (B, C)

The single query behind every weekly section. Run once with `:week_start`/`:week_end`, once with
`:prev_week_start`/`:prev_week_end`.

```sql
WITH user_schemes AS ( /* as §9.2 */ ),
latest_wq AS ( /* as §9.2 */ ),
scheme_fhtc AS ( /* as §9.3 */ ),
supply AS (
    SELECT f.scheme_id,
           COUNT(DISTINCT f.date) FILTER (
               WHERE (f.submission_status = 1 OR f.submission_status IS NULL) AND f.water_quantity > 0
           )::int AS supply_days,
           COALESCE(SUM(CASE WHEN (f.submission_status = 1 OR f.submission_status IS NULL)
                              AND f.water_quantity > 0
                             THEN f.water_quantity ELSE 0 END), 0)::bigint AS litres_week
    FROM latest_wq f
    JOIN user_schemes us ON us.scheme_id = f.scheme_id
    WHERE f.tenant_id = :tenant_id
      AND f.date BETWEEN :week_start AND :week_end
    GROUP BY f.scheme_id
)
SELECT sf.scheme_id,
       sf.fhtc,
       COALESCE(sp.supply_days, 0) AS supply_days,
       COALESCE(sp.litres_week, 0) AS litres_week,
       CASE WHEN sf.fhtc > 0
            THEN ROUND(COALESCE(sp.litres_week, 0)::numeric / (sf.fhtc * :pph * 7), 1)
            END AS scheme_lpcd_week          -- NULL when fhtc = 0: undefined, not zero
FROM scheme_fhtc sf
LEFT JOIN supply sp ON sp.scheme_id = sf.scheme_id
ORDER BY sf.scheme_id;
```

From this single result set:

| Figure                                | Derivation                                                                                |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| B §1 Schemes Supplying Water          | `COUNT(*) WHERE supply_days >= 1`                                                         |
| C §1 Schemes Supplying Water          | `COUNT(*) WHERE supply_days >= 4`                                                         |
| B/C Schemes Not Supplying             | `COUNT(*) WHERE supply_days = 0`                                                          |
| B §2 / C §3 list                      | rows `WHERE supply_days = 0`                                                              |
| B §3 list                             | rows `WHERE supply_days BETWEEN 1 AND 3`                                                  |
| B §4 / C §4 list, C §1 ≤15 LPCD count | rows `WHERE scheme_lpcd_week <= 15 AND supply_days >= 1`                                  |
| B/C Average LPCD                      | `ROUND(SUM(litres_week)::numeric / NULLIF(SUM(fhtc) * :pph * 7, 0), 1)` over **all** rows |

Note the last row sums `litres_week` and `fhtc` across the whole set before dividing — it is _not_ the
average of the per-scheme LPCD column, which would weight a 10-connection scheme the same as a
10,000-connection one.

## 10. Privacy

Phone numbers are PII. They appear at `DEBUG` level only — never in `INFO`, `WARN` or `ERROR` lines,
in application code, tests or helpers. `title` and `phone_number` are AES-encrypted at rest and
decrypted through `PiiEncryptionService.safeDecrypt` at render time only. analytics-service holds no
PII at all and must not be given any: if a future field needs a name or a number, resolve it in
message-service from the operational schema, as every existing field does.
